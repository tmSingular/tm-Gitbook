# Message format and timestamps

Distinguish the publisher’s JSON from the client callback’s message envelope. This prevents the common mistake of reading `message.text` instead of `message.payload.text`.

## Published JSON versus received data

Publisher sends:

```json
{ "text": "First update" }
```

For the client’s `message` status, the application reads the same data at `message.payload`. This is a partial illustration of the callback object, not a complete backend schema:

```json
{
  "payload": {
    "text": "First update"
  }
}
```

The callback can contain additional metadata. Do not send the illustrated envelope as the publishing body unless your application intentionally wants an additional nested `payload` field.

## Retained latest value

A stream retains the latest published payload until a newer publication arrives. A client connecting to that stream receives its retained latest payload. This supports initialization from the current feed state without waiting for a new provider update.

Retained data is not necessarily fresh data. The latest value may have been published long before the current Player connected. No event-history replay or ordered delivery of every intermediate update is established by this behavior. Avoid using the retained payload as an unguarded one-shot action such as increment, play, or reset.

Send complete application snapshots when consumers need a coherent set of fields. This section does not assert field-level merge semantics for partial publication or replay guarantees after reconnect.

## Backend timestamps

The Data Stream service adds UTC timestamp metadata to payload delivery. The available contract does not specify its exact property path, representation, or units. Consequently these examples do not invent `message.timestamp`, treat the whole envelope as application data, or assume seconds versus milliseconds.

Before using service metadata in production arithmetic, establish that field’s exact client contract for the deployed version. For a timestamp you control today, define one in your own application payload.

## Application-defined publisher timestamp

For example, agree that `updatedAtMs` is an integer Unix timestamp in milliseconds generated by the publisher when it creates a sample:

```json
{
  "text": "First update",
  "updatedAtMs": 1893456000000
}
```

That timestamp represents 2030-01-01 00:00:00 UTC and is illustrative; a real publisher sends its current sample timestamp on each update. `updatedAtMs` is an application field, not a reserved Data Stream field.

At receipt, a compatible consumer can compare `Date.now()` with `message.payload.updatedAtMs`. The difference estimates age only when the publisher and consumer clocks are comparable. Clock skew can produce a misleading or negative result; it is not automatically network transit time or a server-measured latency.

Record local receipt time separately when you need “time since the last callback.” That measure cannot distinguish newly published data from an old retained value. Choose a freshness policy appropriate to the feed and explain it to the graphic’s operator.
